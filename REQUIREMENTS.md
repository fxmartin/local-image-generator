# REQUIREMENTS — local-image-generator

> Generated by `/brainstorm` on 2026-09-24 from `PROJECT-SEED.md` and an interview
> with the owner. Single user, three machines, no cloud. Consumed by `/generate-epics`.

## 1. Executive Summary

FX does not generate images today. Cloud image services are off the table for
privacy and habit reasons, and the existing local tooling (ComfyUI graphs,
diffusers venvs) is too much friction to become a habit. `local-image-generator`
(`lig`) is a Python CLI that turns a prompt into a 1K–2K PNG with Qwen-Image-2.1
on FX's own hardware, first on the Dell XPS 13 (Intel Arc 140V iGPU), then by
delegating to the M3 Max over the tailnet, then natively on the Macs via MLX.
Success is binary: one documented command produces a usable image on every
machine, and generate / edit / seed-compare / bench all work from a fresh clone.

## 2. Context & Strategic Rationale

**Why now.** Qwen-Image-2.1 shipped on 2026-09-20: a 7B single-stream DiT with a
Qwen3-VL text encoder that does generation, instruction editing and transparent
output in one checkpoint, with guidance-free 40-step sampling. Within four days
the ecosystem has produced GGUF quantizations (unsloth, leejet), an
stable-diffusion.cpp integration with official docs, an MLX path (mflux
`mflux-generate-qwen-2.1`, 4-bit MLX conversions), an ncnn/Vulkan port claiming
full BF16 on 2 GB of dedicated GPU memory, PyTorch XPU recipes for Intel Arc, and
day-zero (experimental) OpenVINO support. The model is good enough to be fun and
runnable on consumer hardware. That combination did not exist a month ago.

**Strategy fit.** FX runs a personal AI lab across three machines
(`macbook-pro-m3-max`, `home-lab` M1 Pro, `omarchy-xps13`) managed by nix-darwin
and omarchy-install, with a local GitLab CI stack. Image generation is the missing
capability; the remote-engine requirement mirrors how the LLM side already works
(big box serves the laptop over Tailscale). Keeping work on-desk is the point, not
the API bill.

**Competitive landscape (what FX would use instead).**

| Option | Why not |
|---|---|
| ComfyUI + ComfyUI-GGUF | Node graphs and a web UI for a one-command need; heavy install; no remote story beyond exposing the whole UI. |
| Hugging Face diffusers scripts | Works, but torch XPU on Lunar Lake is under-documented; every script is a bespoke venv. |
| Radiant Canvas (macOS app) | Mac only, GUI, closed engine; no XPS, no scripting. |
| Unsloth Desktop | Desktop app, not scriptable, no remote. |
| Raw `sd-cli` / `qwenimage-ncnn-vulkan` / `mflux-generate-qwen-2.1` | Each is one backend on one platform with its own flags and no model management. `lig` wraps exactly these. |

The product is the glue: one CLI, one config, one model cache, one output
convention, N engines.

## 3. User Problems & Jobs-to-be-Done

**Persona: FX, sole user.** Senior engineer, C-level context, runs everything
local-first. Wants illustrations for docs, slides and blog posts, and fan-art /
exploration for fun. Works on the XPS 13 most of the day; the M3 Max is the strong
box; the M1 Pro home-lab is always on.

**Jobs.**

1. "I'm writing a post and need a hero image now." → `lig generate "..."` and a
   PNG appears in `outputs/` with its prompt and seed recorded.
2. "The image is 90% right, change one thing." → `lig edit last.png "make the
   teapot cobalt blue"` without touching the rest.
3. "Which of these compositions is best?" → `lig seeds "..." --count 4` renders a
   contact sheet of seed variants.
4. "Is this the fastest my hardware can go?" → `lig bench` times every installed
   engine on the same prompt and records the result.
5. "The XPS is slow, use the Mac." → `lig generate "..." --host m3max` (or
   configured default) runs the job remotely and brings the PNG back.
6. "Which weights do I have, are they intact, how much disk?" → `lig models list /
   pull / verify / rm`.

**Current workaround.** None. FX does not generate images; the job goes undone or
gets a stock image. That is the pain.

**Journey friction points (from the reference article and the ecosystem survey).**

- First run: 10–35 GB of weights across 3–4 files with no single canonical
  source; wrong VAE version silently breaks output.
- Every engine has different flags for the same concept (steps, cfg, seed, size).
- Image dimensions must be multiples of 32; editing quality is resolution-sensitive
  (1K edits smeared unrelated textures in the article, 2K did not).
- Peak memory: ~72 GiB BF16 vs ~21 GiB for a Q4 transformer + Q8 text encoder
  recipe. The XPS has 30 GB shared RAM; the choice is forced, not optional.
- No record of what prompt/seed made which file once `outputs/` has 200 PNGs.

## 4. Solution Overview

**Approach.** A Typer CLI over a `Backend` protocol. Standalone engines
(`sd-cli` from stable-diffusion.cpp, `qwenimage-ncnn-vulkan`) are wrapped as
subprocesses; Python-native engines (mflux on MLX; optionally diffusers on torch
XPU) are in-process adapters. A `RemoteBackend` speaks HTTP to a `lig serve`
daemon on another host that exposes whichever local backend that host has. All
backends consume the same `GenerateRequest` / `EditRequest` and emit the same
`ImageResult` (PNG bytes + metadata). Model artifacts come from a curated registry
(repo, filename, sha256, size, which engine consumes it) and live in one cache.

**Key capabilities.** generate, edit, seeds (contact sheet), bench, models,
serve, config. Deterministic output naming and sidecar metadata.

**Not building (v1).**

- No GUI or web UI. No gallery. Open the file.
- No LoRA, fine-tuning or training. Inference only.
- No models other than Qwen-Image-2.1. The protocol may permit others later; zero
  effort is spent on it.
- No auth, TLS, multi-user or rate limiting on the daemon. The tailnet is the
  perimeter.
- No prompt-rewriter LLM in Phase 1 (P2, see §5).
- No video (the article's next experiment is explicitly out).

**Architecture.**

```
lig (Typer CLI)
 ├─ cli/         generate · edit · seeds · bench · models · serve · config
 ├─ core/        GenerateRequest / EditRequest / ImageResult · output naming · metadata
 ├─ backends/    Backend protocol
 │    ├─ sdcpp     subprocess → sd-cli (Vulkan | SYCL | Metal builds)
 │    ├─ ncnn      subprocess → qwenimage-ncnn-vulkan
 │    ├─ mlx       in-process → mflux QwenImage21           (Phase 3)
 │    └─ remote    HTTP client → lig serve on another host  (Phase 2)
 ├─ models/      registry (YAML) · downloader (resume, sha256) · cache · disk report
 └─ server/      FastAPI daemon wrapping one local backend   (Phase 2)
```

Config precedence: CLI flag > env `LIG_*` > `~/.config/lig/config.toml` >
built-in defaults. Model cache at `$XDG_CACHE_HOME/lig/models` (override
`LIG_MODELS_DIR`). Outputs default to `./outputs`.

## 5. Detailed Requirements

Sampling defaults, all engines: 40 steps, seed random unless given, size
1024×1024, output PNG. Engine-specific guidance defaults are owned by the adapter
(guidance 1.0 everywhere, Euler for sd.cpp: Qwen-Image-2.1 is guidance-free, and on
the XPS sd.cpp's documented cfg 6.0 doubled the time for no visible gain). Sizes are validated to multiples of 32 before any engine is invoked.

### P0 — Must have (Phase 1, XPS local)

| ID | Requirement | Acceptance |
|---|---|---|
| P0-1 | `lig generate PROMPT [--size WxH] [--steps N] [--seed S] [--engine E] [--out DIR]` produces a PNG. | Fresh clone + README steps → 768², 30-step PNG in `outputs/` in ≤ 10 min wall-clock on the XPS 13 (140V iGPU, 30 GB RAM), the local fallback chosen in Story 02.1-004 (measured 398 s). Full 1024², 40-step images from the XPS render remotely (P1-2). |
| P0-2 | `lig edit IMAGE PROMPT [...]` applies an instruction edit to an existing PNG. | Edited PNG produced; test uses a fake backend; manual check on XPS that a single-object recolor leaves the rest visibly intact at 1024². |
| P0-3 | `lig seeds PROMPT --count N [--seed-start S]` renders N seeds and a contact sheet. | N PNGs + one `*_sheet.png` grid with seed labels; N ≤ 8 enforced. |
| P0-4 | `lig bench [--engines a,b] [--size] [--steps]` times each installed engine on a fixed prompt/seed and writes `bench/<date>_<host>.json` + a table to stdout. | Records engine, build backend, size, steps, load time, per-step time, total, peak RSS; refuses to compare results from different hosts. |
| P0-5 | Engine bake-off on the XPS: sd.cpp Vulkan and qwenimage-ncnn-vulkan are integrated and benchmarked; sd.cpp SYCL and diffusers/torch XPU are attempted and either integrated or documented as rejected with numbers. | `docs/bench/xps13.md` names the default engine for the XPS with measured times. The default in config is set from this. |
| P0-6 | `lig models list / pull [NAME] / verify / rm / path` against a curated registry (YAML checked into the repo) with repo, filename, sha256, size, engine, role (transformer / text-encoder / vae / mmproj). | `pull` resumes partial downloads, verifies sha256, refuses to overwrite a verified file; `list` shows installed/missing and disk usage; `verify` exits non-zero on mismatch. |
| P0-7 | Deterministic output naming and metadata: `YYYYMMDD-HHMMSS_<prompt-slug>_s<seed>.png` plus sidecar `.json` (prompt, negative, seed, steps, size, engine, engine version, weights + hashes, timings, host) and the same fields as PNG `tEXt` chunks. | Sidecar validates against a pydantic schema; `lig edit` records the source image path and hash. |
| P0-8 | Config file + env + flags with the stated precedence; `lig config show` prints the effective config and where each value came from. | Unit-tested precedence matrix. |
| P0-9 | Engine discovery: each backend reports `available()` with a reason string (binary missing, weights missing, unsupported platform). `lig doctor` prints the table. | On the XPS, `doctor` shows Vulkan ICD present, no oneAPI, no Metal, and which weights are cached. |
| P0-10 | Tests run offline, without weights, without a GPU: a `FakeBackend` that emits a valid PNG; subprocess adapters tested against a stub `sd-cli`. | Suite green in the local GitLab CI container (Linux/arm64, root, no network). |
| P0-11 | README: install (`uv tool install`), engine build/install per platform, first-run weight pull, the five commands. | A colleague-proof walkthrough; FX runs it on a clean shell. |

### P1 — Should have (Phase 2 remote, Phase 3 MLX)

| ID | Requirement | Acceptance |
|---|---|---|
| P1-1 | `lig serve [--engine E] [--bind 0.0.0.0:7860]` FastAPI daemon exposing `POST /v1/generate`, `POST /v1/edit`, `GET /v1/health`, `GET /v1/models`; streams progress (SSE) and returns PNG + metadata. | Runs on the M3 Max; health lists engine, loaded weights, idle state. |
| P1-2 | `RemoteBackend`: `--host NAME` or config `default_host`; uploads the reference image for edits; downloads the PNG and writes the same local naming/metadata (plus `remote_host`). | From the XPS, `lig generate "..." --host m3max` produces a local file identical in convention to a local run. |
| P1-3 | Daemon keeps the engine warm with an idle-unload TTL (default 10 min, configurable, `0` = exit after each job as in the reference setup). | Memory returns to baseline after TTL; verified with the health endpoint. |
| P1-4 | `mlx` backend via mflux `QwenImage21` with `-q 8` default on the Macs, bf16 optional. | `lig bench` on the M3 Max shows MLX vs sd.cpp Metal; default for macOS set from the numbers. |
| P1-5 | sd.cpp Metal build wrapped for the Macs before MLX lands, so Phase 2 has an engine to serve. | Bench numbers recorded in `docs/bench/m3max.md`. |
| P1-6 | Transparent PNG output (`--transparent`) where the engine supports it. | RGBA PNG with real alpha on sd.cpp; documented as unsupported elsewhere. |
| P1-7 | `lig models pull --for ENGINE` pulls exactly the file set that engine needs on this platform. | No orphan downloads; disk estimate printed before download. |

### P2 — Nice to have

- Prompt rewriter: optional local LLM pass (Qwen's official rewriter or any
  OpenAI-compatible endpoint) that expands the prompt; the expanded prompt is
  saved in the sidecar so it can be reused without re-running the rewriter.
- `lig serve` job queue with concurrency 1 and a queued/running/done state, so
  two clients do not collide.
- OpenVINO backend once Intel validates the pipeline.
- Shell completion, `--open` to launch the image viewer, `--json` output for
  scripting.
- Contact sheet for size variants (same seed, several aspect ratios).

### Non-functional

- **Offline after first pull.** No command other than `models pull` may touch the
  network. Tests never do.
- **Memory safety.** Before launching an engine, estimate peak memory from the
  registry (file sizes + engine overhead) and refuse with a clear message if it
  exceeds available RAM by default; `--force` overrides.
- **Reproducibility.** Same engine build + weights + seed + params → same image on
  the same host; the sidecar holds everything needed to re-run.
- **Errors.** Engine stderr is captured to `~/.local/state/lig/logs/`; the CLI
  shows the last 20 lines and the log path, never a raw traceback.
- **Performance targets.** XPS 13 local: ≤ 10 min per 768², 30-step image (hard;
  measured 398 s). 1024², 40 steps takes 21 min on the XPS, so it renders
  remotely by default (Story 02.1-004, `docs/bench/xps13.md`). M3 Max: ≤ 2 min per 1024² image via MLX.
  Remote overhead from the XPS: ≤ 10 s beyond the Mac's local time for a 1024² PNG.
- **Platforms.** Linux x86_64 (Arch/omarchy) and macOS arm64. Never assume a
  platform; probe with `platform`/`uname`. No Windows.
- **Security.** Daemon binds to the tailnet interface by default, warns loudly if
  bound to `0.0.0.0` without Tailscale present; no auth in v1 by decision.
- **Licensing.** Record the license of every registry artifact; Qwen-Image-2.1
  base is Apache-2.0 but some community conversions carry the Qwen Research
  License. `lig models list` shows it.
- **Code quality.** Python 3.12+, uv, full type hints, ruff, pytest, TDD, ≥ 85 %
  line coverage on `core/`, `models/`, `cli/`; conventional commits.

## 6. Success Criteria & Metrics

Single user, so these are usage facts FX can read off the sidecars, not
dashboards.

**Leading.**

- Phase 1: ≥ 10 images generated on the XPS in the first week after P0 lands.
- Run success rate ≥ 95 % (sidecar written / commands issued), measured from
  `bench` and logs.
- `lig bench` has a recorded result per host in `docs/bench/`.

**Lagging.**

- By end of Q4 2026, every illustration in FX's docs, slides and posts came out
  of `lig` (zero cloud image generations).
- The M3 Max serves the XPS routinely: ≥ 50 % of XPS-initiated images rendered
  remotely once Phase 2 is live.

**Definition of done (Phase 1).**

1. Fresh clone → README → 768², 30-step PNG on the XPS in one documented command, ≤ 10 min.
2. `generate`, `edit`, `seeds`, `bench`, `models` all work on the XPS.
3. `docs/bench/xps13.md` names the winning engine with numbers; config default
   matches.
4. Test suite green in the local GitLab CI container; coverage gate met.
5. README complete; no hardcoded hostnames or paths.

## 8. Risks & Mitigation

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| 140V iGPU is too slow for ≤ 10 min at 1024² (Arc Pro B70 discrete does 52 s; the iGPU is far weaker). | Medium | High: Phase 1 target missed | Phase 0 spike before any product code. Fallbacks: smaller default size on XPS (768²), fewer steps, or declare the XPS a remote-only client and pull Phase 2 forward. |
| sd.cpp / ncnn Qwen-Image-2.1 support is days old and churns (flags, file names, VAE version). | High | Medium | Pin engine commits/releases in the registry; adapters map our request model to engine flags in one place; bench doc records versions. |
| Weight files change or move on Hugging Face; wrong VAE silently degrades output. | Medium | Medium | Registry pins filename + sha256; `verify` command; README warns. |
| Memory: 30 GB shared RAM on the XPS with Q4 transformer + Q8 text encoder (~21 GiB peak in the reference) leaves little headroom with a browser open. | Medium | Medium | Pre-flight memory estimate with refusal; text encoder offload flags; document "close Chrome". |
| sd.cpp Metal has known large-matrix performance issues; Phase 2 on the Mac could be slower than expected. | Medium | Low | Phase 2 only needs correctness; MLX in Phase 3 owns Mac speed. |
| mflux bf16 peaks at ~46 GB; depends on the M3 Max's RAM configuration. | Low | Medium | Default `-q 8`; bench both. |
| Licensing of community conversions (Qwen Research License) vs Apache-2.0 base. | Low | Low (personal use) | Record license per artifact; prefer official/Apache sources. |
| Daemon exposed beyond the tailnet by misconfiguration. | Low | Medium | Bind to tailnet IP by default; loud warning on `0.0.0.0`; no auth is a documented v1 decision. |
